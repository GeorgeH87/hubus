# Protocol Overview

## 1. System Model

HUBUS is a synchronous master-slave bus.

- Master: Raspberry Pi.
- Slaves: ATtiny microcontrollers.
- Bus lines:
  - `CLK`: always generated by the master while bus activity is ongoing.
  - `DATA`: shared line used for intent signaling, arbitration, and payload transfer.

No active bus transceivers, arbiters, or logic components are used beyond master and slave MCUs.

## 2. Roles and Responsibilities

### Master

- Generates the bus clock.
- Starts all communication cycles.
- Sends short control intents.
- Controls when payload is requested.
- Handles timeout and error recovery policy.

### Slave

- Listens for master intents.
- Signals pending communication on `DATA`.
- Participates in arbitration when needed.
- Responds only when selected by master.

## 3. Communication Lifecycle

1. **Idle**
- Master is not currently transferring a frame.
- Slaves are in listen mode.
- A slave with a pending event may pull `DATA` low to announce an event while idle.
- Master confirms event detection by sending clock ticks on `CLK` until the slave releases `DATA`.

2. **Master Intent**
- Master sends a compact control message indicating next action:
  - poll pending messages
  - request information
  - send command

For buffered-data retrieval, the master issues the intent: "Give me your buffered data." A slave without buffered data ignores this request completely and remains silent.

If a slave buffers new status data before the previous buffer content has been read, the new data may overwrite the old data.

All addressed master commands use unified target-mask addressing.

- The command carries `TARGET_LEN` first, then an `MCID` prefix.
- Any slave whose MCID begins with that prefix is addressed.
- `TARGET_LEN=6` is exact single-slave addressing in v0.
- Slaves may reject the frame early when `TARGET_LEN` and the incoming prefix bits prove a mismatch.

The status-capture command uses this same mechanism. Every matching slave that supports status capture stores its current status in its local buffer.

3. **Slave Intent Signaling**
- Slaves with pending data expose intent on `DATA` during defined slots.

4. **Arbitration (if multiple contenders)**
- Slaves send MCID bit-by-bit.
- `1` is represented by pulling `DATA` low.
- Higher MCID has higher priority.
- Losing slaves drop out immediately.
- A losing slave may emit a final handoff indication in a predefined slot before fully releasing `DATA` to tell the master that more pending slaves still exist.

5. **Selection and Transfer**
- Master requests concrete data from the winning MCID.
- Selected slave responds.
- After the response, the master may continue polling until no further handoff indication or contention is observed.
- The master keeps an internal mask of pending MCIDs and uses it to decide which slave is requested next.

### Master Pending Mask Behavior

- The master sets a pending MCID bit when it detects a valid event announcement or a valid contender during arbitration.
- The master clears the bit once that MCID has been served successfully.
- A failed request can be retried up to a small configured budget before the bit is cleared and the slave is treated as unavailable for the current burst.
- The pending mask is internal state; it is not sent on the wire.
- If a master-issued status-capture command causes multiple slaves to buffer data, each slave may keep only the newest unread value.
- If a master-issued status-capture command targets multiple slaves, each matching slave may overwrite its previous unread snapshot with the new one.

If the same slave still has buffered data and wins again, the master may request it again before reaching lower-priority slaves. This is accepted behavior in v0.

6. **Return to Idle**
- Master may repeat polling or continue with another command.

## 3.1 Idle Event Handshake

The idle handshake is level-based and master-clock-confirmed:

1. Slave detects a local pending event and pulls `DATA` low.
2. Master observes low `DATA` while idle and enters event-confirm mode.
3. Master emits one or more clock ticks on `CLK` as confirmation while monitoring `DATA`.
4. Slave releases `DATA` after confirmation ticks are detected.
5. Master proceeds with normal intent flow (typically `POLL_PENDING` or `REQUEST_INFO`).

If `DATA` remains low past a configured threshold, master enters recovery as line-fault handling.

## 3.2 Handoff Slot

When a slave loses arbitration but knows that other slaves still have pending data, it may use one predefined handoff slot to announce "continue polling" before fully releasing the bus.

The handoff slot is not a second arbitration round. It is a short protocol marker that tells the master that at least one other slave is still pending, so the master should continue the burst instead of returning to idle.

The intended model is:

1. Arbitration selects one winner.
2. The winning slave is served first.
3. A losing slave with knowledge of additional pending slaves asserts the handoff slot immediately before it releases the bus.
4. The master reads this as a continuation marker and keeps its pending MCID mask active.
5. The next slave is then requested in priority order by MCID from that mask.

This means the handoff slot is a continuation hint, not a new address or a replacement for MCID arbitration.

## 4. Protocol State Names

- `IDLE`
- `MASTER_INTENT`
- `SLAVE_INTENT`
- `ARBITRATION`
- `TRANSFER`
- `RECOVERY`

## 5. Design Constraints for ATtiny85

- Minimal frame overhead.
- Small fixed-size parsing logic.
- No dynamic memory requirements.
- Deterministic timing windows based on master clock.
- Data integrity is prioritized over bus speed.
- Moderate/slow bus operation is acceptable when it improves robustness.
- Fairness between slaves is not guaranteed in v0; starvation of lower-priority nodes is accepted.
- Buffer overwrite is preferred over queue growth when a slave receives repeated status-capture triggers.

## 6. Example Device Interaction Patterns

The protocol is generic, but the following examples define intended behavior classes:

- Relay and LED slaves: receive commands to switch outputs on or off; status is readable by master at any time.
- Switch slaves: announce state changes via idle event signaling; master then requests state, and may also request state at any time.
- Temperature sensor slaves: primarily polled by master using request-style reads.

These are usage examples only. The protocol does not require these exact device types.
