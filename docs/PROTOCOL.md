# Protocol Overview

## 1. System Model

HUBUS is a synchronous master-slave bus.

- Master: Raspberry Pi.
- Slaves: ATtiny microcontrollers.
- Bus lines:
  - `CLK`: always generated by the master while bus activity is ongoing. Idle level is low.
  - `DATA`: shared line used for intent signaling, arbitration, and payload transfer.

No active bus transceivers, arbiters, or logic components are used beyond master and slave MCUs.

## 1.1 Division of Responsibility

HUBUS deliberately places complexity on the master:

- Slaves have no time base of their own. The master clock is the only clock a slave reacts to.
- Slaves implement no timeouts, retry counters, or line-fault detection.
- Every slave state transition is caused by a `CLK` edge or a master line condition (START, STOP, RESET).
- All timeouts, retries, fault detection, and recovery are master responsibilities.

Corner cases that can only occur very rarely and recover at the next master cycle are accepted and documented (see section 7) rather than prevented with additional slave logic.

## 1.2 Line Conditions

### Bit Transfer

- `DATA` may only change while `CLK` is low.
- `DATA` is sampled on the rising `CLK` edge.
- A transmitter (master or slave) sets the next bit after the falling `CLK` edge.
- The master must keep `CLK` low long enough for slaves to update `DATA` from their ISR (part of `T_CLK`, see `HARDWARE_REQUIREMENTS.md`).

### Control Conditions

A `DATA` change while `CLK` is high never occurs during bit transfer and is therefore reserved for master control conditions:

| Condition | Line behavior | Meaning |
|---|---|---|
| START | `DATA` falls while `CLK` is high | A frame begins. All slaves discard any partial receive/transmit state and start receiving. |
| STOP | `DATA` rises while `CLK` is high | The current frame/transaction ends. Bus returns to idle. |
| RESET | START immediately followed by STOP, with no clock pulse in between | Reset of the communication stack in all slaves (see section 3.3). |

Only the master generates control conditions.

Every START resynchronizes all slaves. A slave that lost track of the bit stream (for example after a lost clock edge) is back in sync at the next frame at the latest.

### Bus Idle

The bus is idle between a STOP (or RESET) and the next START. `CLK` is low during idle.

Idle event signaling by a slave (`DATA` pulled low while `CLK` is low) is distinguishable from START because `CLK` is low.

### Back-to-Back Transactions

STOP leaves `CLK` high until the master lowers it. A master that continues immediately with the next transaction (for example inside a burst, section 3.2) keeps `CLK` high and generates the next START directly: `DATA` rises (STOP) and falls again (START) while `CLK` is high. The bus is then never idle, `CLK` does not fall in between, and no pending slave announces itself between the transactions of a burst (section 3.1). Only the final STOP of a burst is followed by lowering `CLK`.

### Generating Conditions

- START: with `DATA` released (high) and `CLK` low, the master raises `CLK`, then pulls `DATA` low, then lowers `CLK`. The first frame bit follows.
- STOP: with `CLK` low, the master pulls `DATA` low, raises `CLK`, then releases `DATA`. `CLK` returns low for idle.
- RESET: START immediately followed by STOP, without lowering `CLK` in between.

## 1.3 Transactions and Bus Direction

### Driver Rules

- `CLK` is driven only by the master (push-pull).
- `DATA` is open-drain for every node, **including the master**: a node pulls `DATA` low for `1` and releases it for `0`; nobody ever drives `DATA` high. Simultaneous driving therefore never causes an electrical conflict, and a direction change only requires the previous transmitter to release the line.
- One bit per clock period, for every transmitter: set while `CLK` is low, sampled on the rising edge.

### Turnaround Slot

A turnaround slot (`T`) is one clock period in which every node releases `DATA` and the value is ignored. It is inserted wherever the bus changes from master transmission to slave transmission. The slave uses it to evaluate the received frame (CRC valid, address matched, buffer state) and to prepare its first bit.

The master additionally keeps `CLK` low for at least `T_TURNAROUND` before the rising edge of the slot after `T` (`HARDWARE_REQUIREMENTS.md`).

### Transaction Types

| Transaction | Sequence |
|---|---|
| `SEND_COMMAND` | START · master frame · STOP |
| `REQUEST_STATE` / `REQUEST_INFO` / `REQUEST_DATA`, exact (`TARGET_LEN=6`) | START · master frame · `T` · slave frame or silence · STOP or RESET |
| `REQUEST_STATE` / `REQUEST_INFO` / `REQUEST_DATA`, group (`TARGET_LEN<6`) | START · master frame · `T` · `2·(6−TARGET_LEN)` arbitration slots · slave frame of the winner or silence · STOP or RESET |
| RESET | START · STOP |
| Idle event handshake | slave pulls `DATA` low · master clocks until `DATA` is released · (next START) |

Every request that expects a response is a single transaction, whatever its addressing. With exact addressing exactly one slave can answer and no arbitration is needed. With group addressing the matching slaves arbitrate first and the **winner answers in the same transaction**. The losers stay passive until the next START, STOP, or RESET. Group `SEND_COMMAND` stays one-way.

```
SEND_COMMAND:         START | master frame ........................ | STOP
request, exact:       START | master frame ... | T | slave frame ... | STOP/RESET
request, group:       START | master frame ... | T | bk hk ... b0 h0 | slave frame (winner) ... | STOP/RESET
                                                    (b = arbitration bit, h = handoff slot)
```

The arbitration covers only the MCID bits that the target mask leaves open: bits `5−TARGET_LEN` down to `0`, one arbitration bit and one handoff slot each, `2·(6−TARGET_LEN)` slots in total. The shared prefix bits would be identical for all contenders and are not sent (`ARBITRATION.md`).

### Who Drives `DATA`

| Phase | Driven by | Sampled by |
|---|---|---|
| START / STOP / RESET | master | all slaves |
| Master frame | master | all slaves (a slave stops evaluating once the address does not match) |
| Turnaround `T` | nobody | – |
| Arbitration bit | contenders whose MCID bit is `1` | master and contenders |
| Handoff slot | contenders that lost at exactly this bit | master |
| Slave frame | the exactly addressed slave, or the arbitration winner | master |

A slave that is not addressed ignores everything until the next START, STOP, or RESET.

### Response Detection and Length

- Both slave frame type codes (`10` `SLAVE_DATA`, `11` `SLAVE_INFO`) start with `1`. The first bit after `T` is therefore low for every real response.
- With group addressing the same holds for the first bit after the last arbitration slot: every contender that wins sends a frame, so a high first bit means that nobody contended. Arbitration slots alone cannot show a contender, because the open MCID bits of the only contender may all be `0`.
- If the first bit is high, there is no response (empty buffer, unknown MCID, no pending or matching slave, invalid request frame). The master ends the transaction immediately.
- Otherwise the master reads the slave header, takes the payload length from `LEN`, and clocks exactly the remaining header, payload, and CRC8 bits. It then ends the transaction with STOP (valid) or RESET (invalid), see section 3.4.
- The master compares the source MCID in the response with the addressed MCID, or with the winner MCID (prefix plus the sampled arbitration bits) for a group request. A mismatch is treated like a CRC failure.

### Slave Processing Budget

So that one turnaround slot is sufficient, no slave step may require bulk processing:

- CRC8 is computed incrementally, byte by byte, while receiving and while transmitting.
- At the turnaround slot only three checks remain: CRC result, address match, buffer empty or not.

## 2. Roles and Responsibilities

### Master

- Generates the bus clock.
- Starts all communication cycles.
- Sends short control intents.
- Controls when payload is requested.
- Generates START, STOP, and RESET line conditions.
- Owns all timeouts, retries, line-fault detection, and error recovery.

### Slave

- Listens for master intents.
- Signals pending communication on `DATA`.
- Participates in arbitration when needed.
- Responds only when selected by master.
- Reacts only to `CLK` edges and master line conditions; never waits on its own timer.

## 3. Communication Lifecycle

1. **Idle**
- Bus is between STOP/RESET and the next START (see section 1.2).
- Slaves are in listen mode.
- A slave with a pending event may pull `DATA` low (while `CLK` is low) to announce an event while idle.
- Master confirms event detection by sending clock ticks on `CLK` until the slave releases `DATA` (section 3.1).

2. **Master Intent**
- Master sends a compact control message indicating next action:
  - read the current state (`REQUEST_STATE`)
  - read static device metadata (`REQUEST_INFO`)
  - read the event buffer (`REQUEST_DATA`)
  - send a command (`SEND_COMMAND`, including `STATUS_CAPTURE`)

Each slave has exactly one outgoing buffer. A slave with an empty buffer ignores `REQUEST_DATA` completely and remains silent. New buffer content may overwrite unread old content.

Commands are never acknowledged. If the master needs to confirm that a state was established, it reads the state back explicitly with `REQUEST_STATE`.

All addressed master commands use unified target-mask addressing.

- The command carries `TARGET_LEN` first, then an `MCID` prefix.
- Any slave whose MCID begins with that prefix is addressed.
- `TARGET_LEN=6` is exact single-slave addressing in v0.
- Slaves may reject the frame early when `TARGET_LEN` and the incoming prefix bits prove a mismatch.

`SEND_COMMAND` to a group is one-way (master to n slaves): no slave answers it. Anything a slave wants to report afterwards goes through the regular return path (pending flag, idle event handshake, burst). `REQUEST_INFO` and `REQUEST_DATA` with a group mask are answered by exactly one slave, the arbitration winner. See `MESSAGE_FORMAT.md` section 3.1, "Direction Rule".

For a group request only slaves that can answer contend: every matching slave for `REQUEST_INFO`, every matching slave with a state for `REQUEST_STATE`, only matching slaves with pending data for `REQUEST_DATA`. The master therefore chooses with the request type whether it asks "all that exist", "all that have a state" or "only those that have something to deliver"; slaves that do not qualify drop out immediately and take no part in the arbitration. `TARGET_LEN=0` addresses all slaves.

`STATUS_CAPTURE` uses this same mechanism. Every matching slave that supports it writes its current status into its buffer (overwriting unread content) and sets its pending flag.

3. **Slave Intent Signaling**
- Slaves with pending data expose intent by contending in the arbitration that follows a group `REQUEST_DATA`.

4. **Arbitration with Handoff Slots**
- Contending slaves send the open bits of their MCID bit-by-bit, MSB first.
- `1` is represented by pulling `DATA` low. Higher MCID has higher priority.
- Each arbitration bit is followed by a handoff slot. A slave that lost at exactly that bit pulls `DATA` low in the handoff slot, then stays passive.
- From the handoff slots, the master derives prefix masks for the remaining pending slaves (see `ARBITRATION.md`).

5. **Selection and Transfer**
- The winner sends its `SLAVE_DATA` frame directly after the arbitration, in the same transaction.
- The master continues with the next prefix mask from its pending mask stack (section 3.2) until the stack is empty.

6. **Return to Idle**
- When the pending mask stack is empty, the burst ends and the bus returns to idle.
- A slave that is still (or again) pending announces itself via the idle event handshake, which starts the next burst.

## 3.1 Idle Event Handshake

The idle handshake is level-based and master-clock-confirmed:

1. Slave detects a local pending event and, while the bus is idle and `CLK` is low, pulls `DATA` low.
2. Master observes low `DATA` while idle and enters event-confirm mode.
3. Master emits clock ticks on `CLK` as confirmation while monitoring `DATA`, until `DATA` is released.
4. Slave releases `DATA` after the first falling `CLK` edge, i.e. after one complete clock pulse (releasing while `CLK` is high would look like a STOP). If several slaves signal at the same time, all release after that pulse.
5. Master starts a burst (group `REQUEST_DATA`, section 3.2), beginning with a START condition.

### When a Slave Announces Itself

A slave pulls `DATA` low (event signaling) in exactly two situations, both with `CLK` low and the bus idle:

1. The application writes the buffer while the slave had no pending data (the flag changes from 0 to 1). Overwriting data that is already pending does not signal again.
2. The first falling `CLK` edge after a STOP or RESET, if the slave still has pending data. This is how a slave that was skipped in a burst, or that has data written during a transaction, announces itself again.

A slave signals at most once per STOP. In particular it does not signal again on the clock pulses of an idle event handshake, and not at all on a falling `CLK` edge that follows a START. Without this rule, pending slaves in different phases would keep each other's signals alive and the master could never see `DATA` released.

Master side: before every START (and RESET) with `CLK` low, the master checks `DATA`. If it is low it runs the handshake first. After raising `CLK` for the condition it checks `DATA` once more: a slave that started signaling just before `CLK` rose (section 7.1) holds `DATA` low, and the master lowers `CLK` again, which releases the slave, and repeats the transaction.

The slave has no timeout for this handshake. If no master is running, the slave keeps `DATA` low indefinitely; this is harmless and is resolved by the master startup sequence (section 3.3).

If `DATA` remains low past a configured number of clock ticks, the master treats it as a line fault (master-side policy).

## 3.2 Burst: Handoff Slots and Pending Mask Stack

A burst collects data from all slaves that are pending when it starts, in descending MCID order, with exactly one transaction per pending slave: a group `REQUEST_DATA` whose arbitration winner sends its data directly.

### Principle

A slave that loses arbitration at bit `k` shares bits above `k` with the winner and has `0` where the winner has `1`. Its MCID therefore lies in the group:

`prefix = winner bits above k, followed by 0`, with `TARGET_LEN = (number of bits above k) + 1`.

The handoff slot after bit `k` tells the master whether such a slave exists. The master stores the resulting prefix mask and requests that group later.

### Master Algorithm

1. Start with an empty pending mask stack and send `REQUEST_DATA` with `TARGET_LEN=0`.
2. Evaluate the transaction:
   - First bit after the arbitration slots high: no contender, the group has no pending slave.
   - Otherwise: the winner MCID is the group prefix followed by the sampled arbitration bits. For every handoff slot in which `DATA` was low, push the corresponding prefix mask.
3. The winner's `SLAVE_DATA` frame follows in the same transaction. If it is valid, the master ends the transaction with STOP. If not, it ends with RESET and retries the winner with an exactly addressed `REQUEST_DATA` (section 3.4); the masks are already on the stack.
4. Pop the top mask from the stack and send `REQUEST_DATA` with that prefix; continue with step 2.
5. When the stack is empty, the burst is complete.

Masks pushed later have longer prefixes and cover higher MCIDs, so last-in-first-out order yields strictly descending MCID order. The stack holds at most one mask per prefix length (at most 6 entries in v0).

A mask with `TARGET_LEN=6` identifies one MCID exactly; the request has no arbitration slots and is the same transaction as a retry.

All transactions of a burst are generated back-to-back with `CLK` held high after each STOP (section 1.2), so pending slaves do not announce themselves in between. The master lowers `CLK` after the final STOP; slaves that are still pending then signal again (section 3.1).

### Properties

- Every slave pending at burst start is served within that burst. A higher-priority slave that becomes pending again during the burst lies outside the remaining masks and is served in the next burst. Lower-priority slaves are therefore not starved.
- Slave effort is minimal: one extra drive-low in the handoff slot directly after losing.
- The stack is master-internal state and is never transmitted.
- A failed request can be retried up to a small configured budget; afterwards the slave is skipped for the current burst. Its data stays buffered and it announces itself again later.

### Accepted Rare Cases

- A handoff slot falsely read as low (noise) creates a mask that yields no contender. The request is simply wasted.
- A missed handoff slot leaves a slave out of the current burst. Its pending flag remains set, so it announces itself again via the idle event handshake.

## 3.3 Communication Stack Reset

RESET (START immediately followed by STOP, section 1.2) resets the communication stack of every slave.

### Reset Scope

| Reset by RESET | Preserved across RESET |
|---|---|
| Protocol state (back to idle listen) | Slave buffer content |
| Receive bit buffer / partial frame | Generation counter |
| Arbitration state | Static device info |
| Transmit position / partial response | Pending flag (unread data still exists) |
| `DATA` driver (released) | MCID and application state |

Because the pending flag survives, a slave that still holds unread data announces it again via the idle event handshake after the reset.

### Master Startup Sequence (mandatory)

1. Clock `CLK` until `DATA` is high. Any slave still transmitting or arbitrating finishes within one maximum frame length; a slave in idle event signaling releases on the confirmation ticks.
2. If `DATA` is still low after the master's line-fault threshold (in clock ticks, at least one maximum frame length), report a hardware line fault.
3. Generate RESET.
4. Run a full burst (section 3.2) to collect data that was pending before the reset.

### Master Shutdown (optional)

The master SHOULD generate RESET before it stops, leaving all slaves in a defined idle state with `DATA` released. Slaves must not depend on this, since the master may stop unexpectedly.

### Master Error Recovery

Whenever the master detects a fault (missing response, CRC failure, source MCID mismatch, unexpected line state), it uses the same sequence as steps 1–3 of the startup sequence and then continues with normal operation.

Since every START already resynchronizes slave reception, an explicit RESET is mainly needed at startup and after errors where a slave may be in a transmit or arbitration state.

## 3.4 Transaction End and Buffer Clearing

There is no acknowledgement in either direction. The master confirms a received `SLAVE_DATA` frame implicitly by how it ends the transaction:

| Master ends with | Meaning | Slave action |
|---|---|---|
| STOP | Response received and CRC valid | Clear buffer and pending flag, if a complete `SLAVE_DATA` response (including CRC8) was transmitted in this transaction. |
| RESET | Response missing, incomplete, or CRC invalid | Keep buffer and pending flag (RESET preserves them, section 3.3). |

Rules:

- The slave clears only if it transmitted its complete response in the current transaction. A STOP after an aborted or partial response clears nothing.
- `SLAVE_INFO` is static; nothing is cleared after `REQUEST_INFO`.
- A state frame (`REQUEST_STATE`) is a live read; nothing is cleared after it either. Only a complete event frame (`REQUEST_DATA`) clears buffer and pending flag.
- After a RESET the master may retry with an exactly addressed `REQUEST_DATA`, within its retry budget. When the budget is exhausted it skips the slave for the current burst; the data stays buffered and the slave announces itself again later.

### Accepted Rare Cases

- **STOP corrupted or missed:** the slave keeps its data and announces it again, so the master receives the same data twice. The `GEN` counter in the slave header lets the master detect the duplicate (`MESSAGE_FORMAT.md` section 4.3).
- **Application writes the buffer during transmission:** the transmitted frame may mix old and new content, and the following STOP clears the new content. The library SHOULD prevent this cheaply (for example by deferring application writes while a response is in progress, or by not clearing if the buffer was written during transmission). Otherwise it is an accepted rare case.

## 3.5 Commissioning Scan and Duplicate MCID Detection

Duplicate MCIDs are a configuration fault. They are detected by the master only; slaves implement no detection logic.

### Commissioning Scan

The master enumerates the slaves with group `REQUEST_INFO`, using the same mask stack algorithm as the burst (section 3.2) with `REQUEST_INFO` instead of `REQUEST_DATA`. Every slave matching the mask contends, so the winner's `SLAVE_INFO` arrives in the same transaction and the scan needs about one transaction per slave. Empty MCID groups are never visited.

- valid `SLAVE_INFO`: slave present (protocol version and capabilities known),
- no contender: no slave in that group,
- repeated CRC failures for a winner: suspected duplicate MCID or line problem. The master repeats the request for that MCID with exact addressing (`TARGET_LEN=6`) within its retry budget.

Two slaves with the same MCID win the arbitration together and both send their `SLAVE_INFO`. The responses overlap on the wired-AND line. If their content differs, the CRC fails, so the scan flags the duplicate right away. Slaves SHOULD therefore include a device-unique value (for example a serial number set at programming time) in the application bytes of `SLAVE_INFO` (`MESSAGE_FORMAT.md` section 4.1); then the scan detects duplicates reliably.

A master can also ask for a single MCID with an exactly addressed `REQUEST_INFO` at any time (for example `hubusd` on request over MQTT); there is no function that polls all 63 MCIDs one by one.

### Runtime Heuristic

If the same MCID fails CRC repeatedly while other MCIDs respond cleanly, the master reports "suspected duplicate MCID". Repeated failures for many MCIDs point to a line problem instead.

### Accepted Limitations

Without a device-unique value in `SLAVE_INFO`, a duplicate MCID can remain unnoticed as long as only one of the affected slaves has buffered data, or their responses are identical. Commands addressed to that MCID reach both slaves.

## 4. Protocol State Names

- `IDLE`
- `MASTER_INTENT`
- `SLAVE_INTENT`
- `ARBITRATION`
- `TRANSFER`
- `RECOVERY` (master only; slaves have no recovery state, they are reset by START/RESET)

## 5. Design Constraints for ATtiny85

- Minimal frame overhead.
- Small fixed-size parsing logic.
- No dynamic memory requirements.
- No slave timers or timeouts.
- Deterministic timing windows based on master clock.
- Data integrity is prioritized over bus speed.
- Moderate/slow bus operation is acceptable when it improves robustness.
- Within a burst, priority decides only the order; every slave pending at burst start is served (section 3.2).
- One outgoing buffer per slave; overwrite is preferred over queue growth.
- No acknowledgement or error frames from slaves.

## 6. Example Device Interaction Patterns

The protocol is generic, but the following examples define intended behavior classes:

- Relay and LED slaves: receive application commands (`SEND_COMMAND`) to switch outputs on or off. To verify, the master reads the state with `REQUEST_STATE`.
- Switch slaves: write state changes into the buffer and announce them via idle event signaling; the master collects them in a burst. The slave also exposes the current level of all its inputs as state, which the master may read at any time with `REQUEST_STATE`.
- Temperature sensor slaves: expose the measured value as state (`REQUEST_STATE`, single slave or group). `STATUS_CAPTURE` still lets the master collect values through a burst.

These are usage examples only. The protocol does not require these exact device types.

## 7. Accepted Rare Cases

The following corner cases are known and accepted in v0. They are rare and recover without additional slave logic.

### 7.1 Event Signal Races With START

A slave decides to start idle event signaling while `CLK` is low, but the master raises `CLK` for a START before the slave's write takes effect. Other slaves then observe a `DATA` fall while `CLK` is high and interpret it as a START.

- Effect: the signaling slave interprets the first frame clock ticks as confirmation ticks and releases `DATA`; the frame being sent is corrupted and fails CRC or address matching in all slaves.
- Recovery: the master detects the corruption by reading back `DATA` while transmitting (or by a missing response), treats it as a pending event, and repeats the transaction. The next START resynchronizes all slaves.

### 7.2 Master Stops Mid-Transaction

If the master stops clocking mid-frame, slaves remain in their current state, possibly holding `DATA` low.

- Effect: bus is blocked until the master restarts.
- Recovery: master startup sequence (section 3.3).
