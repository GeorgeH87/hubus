# Decisions

Why HUBUS is the way it is. Each entry states the decision, the reason, rejected alternatives where there were any, and where it is specified. The specification itself is the reference; this log only explains it.

## Principles

- **Lightweight slaves, complexity on the master.** ATtiny devices have tiny flash and RAM; the Raspberry Pi has resources to spare. Every design question is decided in favor of a simpler slave ([overview](../overview.md#design-principles)).
- **No timeouts on the slave.** The master clock is the slave's only time base; all timeouts, retries, and recovery are master-side. A blocked bus is released by the master's clock pulses and RESET ([§7.6](../spec/07-slave.md#76-no-timeouts), [§6.6](../spec/06-operation.md#66-startup-shutdown-and-recovery)).
- **Rare, self-recovering corner cases are accepted** and documented instead of prevented with slave logic ([§8](../spec/08-faults.md)).

## Physical Layer and Framing

- **`DATA` low = `1`, open drain for every node including the master.** Wired-AND makes the arbitration work and avoids electrical conflicts when the transmitter changes ([§1.1](../spec/01-physical-layer.md#11-bus-lines)).
- **3.3 V bus without level shifters** (2026-10-21). Raspberry Pi GPIOs are not 5 V tolerant, and a 5 V ATtiny has no reliable input margin for 3.3 V signals ([§1.2](../spec/01-physical-layer.md#12-logic-levels-and-voltage)).
- **Master clock, timing values as minimums.** A jittery user-space clock only slows the bus down; the master sets the minimums for the slowest slave ([§1.4](../spec/01-physical-layer.md#14-timing-parameters)).
- **Slaves declare a speed class, not a clock rate** (2026-10-26). The response time of a slave depends on its firmware (CPU clock, the application's own interrupts), not only on the device, so only the firmware can state it. Four bits give classes `1..15` from 1024 µs down to 8 µs, halving every two classes; `0` means not declared. A finer scale would promise a precision that a jittery master clock does not have. Every slave watches every edge to tell line conditions from bits, so `T_CLK_LOW` and `T_COND` always respect the slowest slave on the bus; only the rest of a frame after the slower slaves have rejected its prefix can be clocked for the addressed ones ([§1.5](../spec/01-physical-layer.md#15-speed-classes)).
- **`SLAVE_INFO` gets a fourth protocol byte for the speed class** (2026-10-26). The free bits of the capability byte would have been used up by the class; a separate byte keeps three capability bits and four bits of byte 3 in reserve, at the cost of one application byte (27 instead of 28) and 8 clock ticks per `REQUEST_INFO`. Done before any slave runs on hardware, so nothing in the field breaks. Rejected: the upper bits of byte 2 (a raw number masters compare against) and a length field for the protocol bytes (the protocol version already fixes the layout) ([§4.7](../spec/04-frames.md#47-slave-info-slave_info)).
- **Blind sections after a command, announced as a blind class** (2026-10-27). A slave that has to disable interrupts for longer than its speed class allows, such as a WS2812 strip driver, would otherwise force a slow clock on the whole bus. Instead it may ignore the bus for a bounded time after a command addressed to it; the four free bits of `SLAVE_INFO` byte 3 announce that time on a logarithmic scale from 0.25 ms to about 4 s, and the master keeps away from that slave only. The class is per slave, not per opcode, to keep `SLAVE_INFO` small; the master waits a few milliseconds after every command to such a slave. At the end of the section the slave takes the current pin levels as its reference and ignores the bus until the next START: with the stale levels from before, the first `DATA` change could look like a START in the middle of a foreign frame, and a header that passes the CRC by chance would let the slave execute a command that was never sent or pull `DATA` low in a foreign handoff slot. Rejected: a "readback supported" field (whether a slave can be read back already follows from capability bits 0 and 1) and a mapping of the values in the master configuration (the firmware has to know what it announces, so the scale belongs to the protocol) ([§7.8](../spec/07-slave.md#78-blind-sections), [§6.9](../spec/06-operation.md#69-blind-time-after-a-command)).
- **START/STOP line conditions delimit frames; RESET = START + STOP** (2026-10-20). Line conditions work without bit synchronization, so every START resynchronizes and RESET always works ([§2](../spec/02-line-conditions.md)).
- **Line conditions are detected with interrupts on both `CLK` and `DATA`.** Rejected: comparing `DATA` at the rising and falling `CLK` edge, which would need only one interrupt pin. With slaves of different interrupt latency, a fast transmitter changes `DATA` after the falling edge before a slow slave has sampled it, which the slow slave would misread as START or STOP ([§7.7](../spec/07-slave.md#77-implementation-notes)).
- **Back-to-back transactions inside a burst, and "announce once per STOP"** (found during implementation, 2026-10-21). Without them, pending slaves pulled `DATA` low after every STOP of a burst and blocked the next START, and slaves in different phases kept each other's signals alive ([§2.4](../spec/02-line-conditions.md#24-back-to-back-transactions), [§6.1](../spec/06-operation.md#61-idle-event-handshake)).
- **16-bit header, identical in both directions, without start-of-frame field** (2026-10-20). Byte-aligned payload and CRC, one parser for both directions; the START is the frame boundary ([§4.1](../spec/04-frames.md#41-frame-structure)).
- **MCID width stays 6 bits (`1..63`), also for v1.** The electrical limits of one open-drain line keep the practical node count well below 63; 8 bits would cost a header byte and 4 arbitration slots per frame. MCID `0` is reserved because it could not win an arbitration visibly ([§4.5](../spec/04-frames.md#45-addressing)).
- **CRC-8/AUTOSAR** (poly `0x2F`, init and final XOR `0xFF`, check `0xDF`; 2026-10-21). Chosen by exhaustive evaluation of all 8-bit polynomials for HUBUS frame lengths: Hamming distance 4 up to 14 covered bytes, every odd-weight error detected, and the non-zero init makes all-zero and all-one frames invalid. The maximum payload stays 31 bytes, with ≤ 12-byte fragments recommended for the strongest integrity ([§4.12](../spec/04-frames.md#412-integrity-check-crc8)).

## Messages

- **Commands are fire-and-forget; no acknowledgement or error frames.** There is no request such a frame could answer; the master reads states back ([§4.4](../spec/04-frames.md#44-command-opcodes), [§4.6](../spec/04-frames.md#46-slave-message-types)).
- **One overwritable event buffer per slave; no queue** (2026-10-20). Overwriting is preferred to queue growth on tiny devices; `GEN` makes overwritten content visible ([§4.8](../spec/04-frames.md#48-event-buffer)).
- **Implicit read confirmation: the STOP after a complete response clears the buffer, a RESET keeps it** (2026-10-20). No acknowledgement frame is needed, and a failed response is retried ([§3.6](../spec/03-transactions.md#36-transaction-end-and-buffer-clearing)).
- **`GEN` and `MORE` in the header instead of sequence numbers** (2026-10-21). Duplicate and overwrite detection and fragments cost no payload; the single buffer keeps fragments in order ([§4.9](../spec/04-frames.md#49-generation-counter-gen), [§4.11](../spec/04-frames.md#411-fragments)).
- **`REQUEST_STATE` next to `REQUEST_DATA`** (2026-10-22). A slave has a current state that the master wants to read at any time, and events that only matter once. Reading the state through `STATUS_CAPTURE` and a burst needed two steps and went through the event buffer, where it could overwrite unread events. The state is read from the application while transmitting, without a copy ([§4.10](../spec/04-frames.md#410-state)).
- **Event buffer and state are independent optional parts; every combination is valid** (2026-10-22). A passive sensor needs no event buffer, which saves about 500 bytes of flash and 39 bytes of RAM; a relay without feedback needs neither, and the master caches its state. Capability bit 2 announces the event buffer ([§7.4](../spec/07-slave.md#74-optional-parts)).
- **Future protocol functions become reserved command opcodes, not message types.** All four master type codes are in use ([§4.3](../spec/04-frames.md#43-master-message-types)).

## Arbitration and Operation

- **Handoff slots and a pending mask stack** (2026-10-20). A slave that loses tells the master where it is, so a burst serves every pending slave in descending MCID order with one arbitration each ([§5.3](../spec/05-arbitration.md#53-slot-sequence), [§5.5](../spec/05-arbitration.md#55-pending-masks)).
- **The winner answers in the same transaction; group requests skip the prefix bits** (2026-10-21). Previously a burst needed two transactions per slave (a `POLL_PENDING` arbitration, then `REQUEST_DATA` to the winner), the scan sent `REQUEST_INFO` to all 63 MCIDs, and every arbitration had 12 slots. Now: one transaction per slave, `2·(6−TARGET_LEN)` slots, and a contender is recognized by the first response bit ([§3.1](../spec/03-transactions.md#31-transaction-types), [§5](../spec/05-arbitration.md)).
- **Commands to a group stay one-way.** Only requests are answered, and only by one slave; results of group commands go through the pending flag and a burst ([§4.5](../spec/04-frames.md#45-addressing)).
- **Fairness through the burst.** A burst serves every slave pending at its start, so a busy high-priority slave cannot starve the others. Priority aging or deferral windows are not planned unless tests show a need; any such policy would be master-side ([open issues](open-issues.md#d3-fairness-strategy)).
- **Duplicate MCIDs are detected by the master only** (2026-10-21): commissioning scan and runtime heuristic. Rejected: detection in the slave, which would hide the configuration fault and add slave logic ([§6.4](../spec/06-operation.md#64-commissioning-scan-and-duplicate-mcids)).

## Implementation

- **Hardware-independent core shared by slave, master, and tests; one HAL per device family** (2026-10-21). The same code runs in the ATtiny interrupt, in the host tests, and in the bus simulation ([slave library](../slave-library.md)).
- **Master in C on Raspberry Pi 3 and newer, GPIO via `libgpiod`, chip selected by label.** Works on every model including the Pi 5; `pigpio` and direct register access are model-specific ([§1.6](../spec/01-physical-layer.md#16-nodes)).
- **Ubuntu 26.04 toolchain** (2026-10-21): `gcc-avr` 14.2 and `avr-libc` 2.2.1 support classic and 0/1/2-series tinyAVR without device packs ([development](../development.md#toolchain)).
- **The application enables global interrupts.** `hubus_slave_init()` only enables the library's pin change interrupts; the application calls `sei()` once its own setup is done ([slave library](../slave-library.md#api)).
- **hubusd: YAML configuration, unknown slaves ignored, MQTT as the only interface.** YAML is the configuration format Home Assistant users know; unconfigured slaves are only listed ([hubusd](../daemon.md)).
- **Firmware update as an optional part, through a separate updater** (2026-10-25). Devices with 8 KB of flash or more can carry the updater (2 KB); smaller ones leave it out without paying anything, and capability bits 3 and 4 tell the master which side answers. The updater is a slave like any other, so the update needs no new message type, only four reserved opcodes ([§6.8](../spec/06-operation.md#68-firmware-update)).
- **Update safety on the slave, the procedure on the master.** The updater checks each page (CRC-16, address, reset vector) and, at every reset, the whole application against its info page; it never starts an incomplete one. Retries, ordering (invalidate first, info page last), and the patching of the reset vector are master-side. `UPDATE_ENTER` needs exact addressing and a key, so no broadcast switches several slaves. Rejected: a boot window in which the updater waits for the master after every reset, which would need a timeout on the slave ([§7.6](../spec/07-slave.md#76-no-timeouts)).
- **The updater runs without interrupts and has its own copy of the core** (2026-10-25). Classic tinyAVR devices have one vector table at address 0, which belongs to the application; polling the pins needs none. Sharing the application's library would tie both firmwares to one build. With link-time optimisation the updater fits into 2 KB of the ATtiny85 ([slave library](../slave-library.md#firmware-update)).

## Master modules

*Draft, 2026-10-29. Supersedes the capability bits, the command size, and the blind class in `SLAVE_INFO`; the speed-class decisions above stay. Spec §4.7, §6.4, §6.9 and §6.10 are rewritten; the other places that mention the removed fields still have to be adapted (see the list below).*

- **A slave firmware image is always delivered with a master module; `SLAVE_INFO` only identifies the module** (2026-10-29). Slaves differ in what the master has to do for them (LED strip animations, for example), so the master needs device-specific code anyway. What a slave used to announce, such as capabilities, command size, blind class, and update support, is then a fixed property of the image and belongs to its module. A second source on the bus could only disagree with the module.
- **`SLAVE_INFO` = protocol version, speed class, hardware identifier** (2026-10-29, HWID 2026-10-31). The speed class stays because the master needs it before it can read the HWID. Supersedes the 1-byte identity of the first draft, which had no version and no device-unique value.
- **Protocol version and speed class share byte 0, four bits each** (2026-10-31). A whole byte for the version was too much for the smallest devices; with the capability and blind bits gone, the speed class needs only its four bits, and a short-form `SLAVE_INFO` is 2 bytes. Sixteen protocol versions are enough, since a later version may redefine everything after the version field. Rejected: keeping reserved bits in this byte (a new protocol version can add fields instead).
- **The hardware identifier (HWID) is separate from the MCID and has a variable length** (2026-10-31). Type, variant, version, hardware revision, and an optional serial number, from the general to the specific; the length comes from `LEN` ([§4.7](../spec/04-frames.md#hardware-identifier-hwid)). Types `0x01..0x7F` are the short form, the type byte alone, so that small devices pay one byte of flash and no serial number handling; `0x80..0xFE` the full form; `0xFF` the updater. Rejected: a length or presence field per element (costs bytes on every device; the type range already says which fields exist) and truncating the full form at any field (a short HWID would be ambiguous between "field absent" and "prefix").
- **The master selects modules by prefix or mask over the HWID** (2026-10-31). A module covers a whole type, a variant, or single versions or revisions with one rule, and the most specific rule wins ([§6.10](../spec/06-operation.md#610-master-modules)). So a firmware change that the master does not care about needs no new module, and one that it does needs only a more specific rule. Rejected: a fixed table per identity, which needed a new identity for every change.
- **Unknown HWIDs are not taken into operation.** There is no capability-based default behavior, so the master needs no code for devices it knows nothing about.
- **The type table is maintained centrally by the development process.** Variants are assigned per type.
- **Duplicate MCID detection depends on the serial number** (2026-10-29, revised 2026-10-31). With a serial number identical devices send different `SLAVE_INFO`, and the scan detects duplicates. Without one two identical devices with the same MCID send identical frames. This rare configuration fault is accepted, as other rare edge cases are.
- **The updater keeps its device information after type `0xFF`** (page size, flash layout, write time; [§6.8](../spec/06-operation.md#68-firmware-update)). These values differ per device and are not a property of one image, so one generic updater module reads them from the bus. Its "updater version" byte stays: with the HWID, versions are no longer excluded.

Still to adapt (not part of this draft): the updater's `SLAVE_INFO` in [§6.8](../spec/06-operation.md#68-firmware-update) (type `0xFF`, then the updater information), the HWID in the slave library (constant part in flash, serial number from EEPROM or signature row) and in hubusd (match rules instead of the device type byte), command size in [§4.4](../spec/04-frames.md#44-command-opcodes), capability bits in [§4.10](../spec/04-frames.md#410-state), [§6.8](../spec/06-operation.md#68-firmware-update), [§7.4](../spec/07-slave.md#74-optional-parts), [§7.8](../spec/07-slave.md#78-blind-sections) (the blind time scale on the wire goes away; the slave still needs its bound), [§8.7](../spec/08-faults.md#87-duplicate-mcid-blind-spots), the glossary, the slave and master library docs, hubusd (profiles replace capabilities), `hubus_slave_core`, the examples, and the tests.
