# Hardware and Electrical Requirements

## 1. Scope

This document defines baseline electrical assumptions for the protocol specification phase.

## 2. Bus Lines

- `CLK`: master output (push-pull), fan-out to all slaves.
- `DATA`: shared wired line for signaling and transfer.

## 3. Shared Data Line Model

- `DATA` is open-drain for all nodes, including the master. No node ever drives `DATA` actively high.
- Slaves and master must support released/high-impedance state on `DATA`.
- A logical `1` is generated by pulling `DATA` low.
- A logical `0` is generated by releasing `DATA`.
- External pull-up resistor keeps released line at high level.

Recommended baseline pull-up range for prototype validation: `2.2k` to `10k`, selected by bus length and node count.

## 4. Voltage Compatibility

HUBUS v0 is a **3.3 V bus**:

- All slaves (ATtiny MCUs) are supplied with 3.3 V.
- The `DATA` pull-up connects to 3.3 V.
- `CLK` is driven by the Raspberry Pi GPIO at 3.3 V logic level.
- No level shifters are used; the bus contains only the Raspberry Pi and the slave MCUs as active components.

Rationale:

- Raspberry Pi GPIOs are 3.3 V only and not 5 V tolerant. A 5 V pull-up would damage the master.
- An ATtiny supplied with 5 V needs about 0.6 × VCC (3.0 V) for a valid high input, which leaves no reliable margin with 3.3 V signals. Supplied with 3.3 V, the threshold is about 2.0 V.
- The ATtiny85 runs from its internal 8 MHz oscillator within its specified operating range at 3.3 V.

Consequences:

- Every slave needs a 3.3 V supply (for example a local regulator if a higher voltage is distributed).
- Loads such as relays may still be switched at 5 V or higher; only the MCU and the bus run at 3.3 V.
- All nodes on one bus use the same 3.3 V logic level; mixed bus voltages are not allowed.

## 4.1 Supported Slave Devices

The slave library is portable across ATtiny devices. All protocol logic lives in a hardware-independent core; a small hardware abstraction layer (HAL) per device family maps pin access and interrupts.

| Family | Examples | HAL |
|---|---|---|
| Classic tinyAVR | ATtiny25/45/85, 24/44/84, 261/461/861, 48/88, 441/841, 2313/4313, 1634 | `DDRx`/`PORTx`/`PINx`, pin change interrupts (`PCMSKx` and related registers, names differ per device) |
| tinyAVR 0/1/2-series | ATtiny202/402/412, 804/814/1614/1616, 3216/3217, 424/824/1624 | `PORTx`/`VPORTx`, per-pin interrupt sense configuration (`PINnCTRL`) |

Requirements:

- **Reference target:** the ATtiny85 is always fully supported, including the maximum payload of 31 bytes in both directions. Every library change must keep the ATtiny85 build within its flash and RAM budget.
- **Minimum device:** 2 KB flash and 128 B RAM. Devices below that (for example ATtiny13A) and the reduced-core devices ATtiny4/5/9/10 are not supported.
- **128 B RAM devices** (ATtiny24/25, 261, 2313/2313A, 202/204/212/214) need shorter buffers: with both buffers at 31 bytes the library takes 94 bytes of RAM, which leaves too little for the stack (the interrupt path alone needs about 40–50 bytes). The build therefore uses 20-byte buffers on these devices by default, so up to 20 bytes of payload per frame in each direction. A slave without the event buffer (`SLAVE_PROPERTIES.md` section 4.2) has only the command buffer and keeps the full 31 bytes.
- **Configurable buffers:** buffer sizes are compile-time options so smaller devices can use shorter buffers. A slave announces the maximum command payload it accepts in `SLAVE_INFO` (`MESSAGE_FORMAT.md` section 4.1).
- **Pins:** `CLK` and `DATA` are build options (`slave/README.md`) and can be any pins that support pin change or edge interrupts (`SLAVE_PROPERTIES.md` section 6). For every classic device listed above the HAL derives the pin change group (register, enable bit, vector) from the port; for other classic devices `HUBUS_CLK_PCGROUP` and `HUBUS_DATA_PCGROUP` name it. On classic devices, placing both pins on the same port keeps them on one interrupt vector.
- **Device selection:** the HAL is selected automatically from the compiler's device macro (`-mmcu=...`); the application only configures pins and buffer sizes.

## 4.2 Supported Master Devices

The master is implemented in C and shares the hardware-independent protocol core with the slave library.

- **Supported models:** Raspberry Pi 3 and newer, including Pi 3B/3B+/3A+, Zero 2 W, Pi 4, Pi 400, Pi 5, and the corresponding Compute Modules.
- **GPIO access:** Linux GPIO character device via `libgpiod`. It works on all supported models, including the Pi 5 whose GPIOs are on the RP1 chip. Direct register access (`/dev/gpiomem`) and `pigpio` are not used: both are model-specific, and `pigpio` does not support the Pi 5.
- **GPIO chip selection:** by chip label, not by number, because chip numbering differs between models and kernel versions.
- **`DATA` line:** requested as open-drain output; the kernel emulates open-drain by switching between input (released) and output low. The master never drives `DATA` high.
- **Timing:** user-space bit-banging. Jitter is tolerated by the protocol (all timing values are minimums). Real-time scheduling priority for the clock thread is recommended.
- **Structure:** the master logic runs on a small HAL (set `CLK`, pull/release `DATA`, read `DATA`, wait). The same master logic runs against a simulated bus in host-side tests.

## 5. Timing Baseline

Master defines these constants:

- `T_CLK`: clock period.
- `T_CLK_LOW`: minimum `CLK` low time; must cover slave ISR latency plus the time a slave needs to update `DATA` after the falling edge.
- `T_SAMPLE`: sample point inside each slot.
- `T_COND`: minimum `CLK` high time around a START/STOP `DATA` transition, so slaves reliably see the condition.
- `T_TURNAROUND`: minimum `CLK` low time before the first slot after a turnaround slot; covers slave frame evaluation (CRC result, address, buffer state) and preparation of the first response bit.
- Line-fault threshold: number of clock ticks after which a `DATA` line that stays low is reported as a hardware fault (master-side, at least one maximum frame length).

A response timeout is not needed: the master detects a missing response from the first bit after the turnaround slot (`PROTOCOL.md` section 1.3).

All timing values are minimums. A slower or jittery master clock only slows the bus down; it never violates the protocol.

Slaves differ in ISR latency (device family, CPU clock; some devices run at 1 MHz by default). The master configures all timing minimums for the slowest slave on the bus.

Slaves have no timing constants of their own; all timeouts are master-side.

Initial values are implementation-dependent and will be frozen after first hardware experiments.

Timing selection principle for HUBUS v0:

- Bus speed is intentionally moderate to improve sampling margin and reliability on ATtiny85-class devices.
- High throughput is not a design target.
- Stable timing and correct frame validation (CRC) take priority over raw transfer rate.

## 6. Layout and Reliability Notes

- Common ground between master and all slaves is mandatory.
- Keep clock and data routing short and clean during early prototypes.
- Add local decoupling capacitors near each MCU.
- Abnormal line states are resolved by the master (clock ticks, RESET), not by slave timeouts.
- A watchdog in slave firmware is optional and application-level only (protection against firmware hangs); it is not part of the protocol.

- No EMI qualification targets yet.
